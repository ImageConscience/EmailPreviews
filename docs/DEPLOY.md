# Deploying

## Environment

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | Database connection. Defaults to `file:./dev.db`. |
| `SESSION_COOKIE_NAME` | Optional. Defaults to `ep_session`. |

Session cookies are marked `secure` when `NODE_ENV=production`, so production
must be served over HTTPS.

## Railway (or any container host) on SQLite

SQLite needs the database file to survive redeploys, which means a volume.

1. Add a volume mounted at `/data`.
2. Set `DATABASE_URL=file:/data/app.db`.
3. Build command: `npm run build` — this runs `prisma generate`, then
   `prisma migrate deploy`, then the Next.js build, so the schema is applied
   before the app starts.
4. Start command: `npm start`.

Without a volume the file lives in the container's ephemeral filesystem and
every deploy starts empty.

## Moving to PostgreSQL

Worth doing once more than a handful of people are editing at the same time —
SQLite serialises writes, which is fine for a small team and not for a large one.

The schema avoids every construct that differs between the two databases, so the
move is:

```bash
# 1. Dump the current data
npx tsx scripts/db-export.ts backup.json

# 2. Switch the provider in prisma/schema.prisma
#      datasource db {
#        provider = "postgresql"
#        url      = env("DATABASE_URL")
#      }

# 3. Point at the new server and rebuild the migration history
export DATABASE_URL="postgresql://user:pass@host:5432/emailpreviews"
rm -rf prisma/migrations
npx prisma migrate dev --name init

# 4. Load the data
npx tsx scripts/db-import.ts backup.json
```

`db-import.ts` refuses to run against a database that already has users, so it
cannot half-merge into a live system. Sessions are not carried over — everyone
signs in again, which is the correct outcome for a database move.

### What to check afterwards

- Row `data` and template `placeholders` are stored as JSON strings in a `String`
  column on both databases; nothing needs converting.
- Roles are plain strings (`owner` / `admin` / `member`), not a database enum,
  so no type needs creating.
- `@default(cuid())` ids are generated by Prisma, not the database, so ids are
  preserved exactly across the copy.

## Backups

`scripts/db-export.ts` is also the backup tool — it writes one JSON file holding
every table except sessions. On SQLite, copying the `.db` file works too, but the
JSON dump is the portable one.
